## R3 · 🟡 渲染图签名**永不过期**（原"鉴权形同虚设"判断错误，已更正）

**更正说明**：本文件 16:12 初版写作"sign 不校验、任何人可遍历全站渲染图"，**结论错误**。错因：alist 对失败请求返回 `HTTP 200 + {"code":401}`，当时只核对了状态码。按响应体复测后的真实结论：

| 凭据 | 响应 |
|---|---|
| 有效 sign | `image/png` 187023B（真图） |
| 无 sign / 错 sign / 垃圾 sign | `application/json` `{"code":401…}` |

且 `x_setting_items.sign_all = true`（全站强制签名），目录浏览对游客关闭（`Guest user is disabled`），文件不存在时同样先返回 401，**无法据响应差异枚举文件名**。所以不存在"任意抓取"与"遍历"问题。

**残留的真实问题**：签名**有效但永不过期**。机制已定位到确切开关——alist 库里 `link_expiration = '0'`（`sign_all = 'true'`），URL 尾部 `…:0` 的那个 `0` 就是过期时间戳位。后果是**凭据一旦外泄即长期可用**（渲染图 URL 会进入 AI 回复文本、群聊记录、后端日志），属于低概率但不可撤销的泄露面。严重度从"任意遍历"降为"泄露后长期有效"。

**处置选项（均需用户确认，不顺手改）**
1. 把 `link_expiration` 从 0 改为正数（小时）。**但单独改这一项会让图片链接集体失效**：`_upload_render_image()` 上传后拿到的绝对直链（含 sign）会被写进 `AIMessage.content`，`public_url()` 只改前缀、**sign 原样保留**，所以链接一旦到期，Web 端历史气泡与 QQ 端已发消息里的图都会裂。必须有选项 2 配套才能开。
2. backend 侧"读时重签"：输出消息前用当前 alist 凭据重新生成 sign（alist 的 sign 是 `HMAC(path+过期时间)`，重签成本低），历史链接随之始终新鲜。代价是每次读多一步计算，且**已发出去的 QQ 消息无法追改**——那些消息里的链接会随有效期到期而失效。
3. 不动 alist，仅收紧日志与文本留存（成本最低，风险降低有限）。

**建议顺序**：选项 2 先落地 → 再把 `link_expiration` 从 0 改为一个大于 QQ 消息合理留存期的值 → 灰度验证新链接到期表现。任何 alist 配置改动属线上变更，需用户点头并留回滚值（当前值 `0`）。

## R6 · 🟡 群消息形态限制（**M0 补齐了次数上限**）

官方文档口径：群消息**不支持流式参数**；被动消息有效时间 5 分钟。
**M0 补充**：群聊**每条用户消息最多被动回复 5 次**（官方「消息收发概述」明确：单聊 4 次 / 群聊 5 次 / 频道 —），
超限错误码 `40034128`「被动回复时间或次数超限」。实测撞线：一次发 7 条，第 6 条即挂。
影响：M3 的双协议在 QQ 端不是「能不能」而是「要攒完整回复再发」；长回答 + 多轮工具调用可能超出 5 分钟窗口；
且**一条用户消息最多只能回 5 条**，多图/多段内容必须合并或分次触发。
处置：QQ 端保留分段发送逻辑，同时验证工具轮数增加后的总耗时上限；分段条数硬上限设为 5。
另注：`msg_type` 是单值 —— 同一条消息里 markdown 与图片**不能共存**（markdown 优先，图片被丢）。

## R10 · 🔴 图片语法缺尺寸提示 → 手机端看不到图（M0 新发现，**最容易踩且最难自查**）

**现象**：markdown 里写标准 `![alt](url)`，**手机端只显示 `[alt]`**，电脑端正常显示。
**根因**：QQ 官方的 markdown 图片语法是 **`![alt #宽px #高px](url)`**（带尺寸提示），
不是标准 markdown 语法。手机端严格按官方语法解析，缺尺寸 → 图片节点建不起来 → 降级成 alt 文本；
桌面端有 fallback 能自行取尺寸，所以**电脑端看不出来**。
**依据**：官方 markdown 文档「图片」小节唯一那张示例就是带尺寸的；
腾讯官方 `tencent-connect/openclaw-qqbot` 专门实现了 Size hint injection（Range 拉前 64KB 解析图片头）。
**影响**：**看起来像"平台不支持嵌图"，实际是自己语法写错了**。这个误判会让整个 D3 走错方向。
处置：
1. 共享包提供**图片尺寸自动探测**（M1 交付），所有 markdown 插图**统一**补 `#宽px #高px`；
2. 探测失败要能降级（走 `ImageSink` 独立图片段），不能直接抛；
3. **任何"渲染/显示"类结论必须手机 + 电脑两端都看**（已写进 `VERIFY.md` V0）。

## R13 · 🟡 尺寸探测的 SSRF 面（未做内网 IP 段拦截）

`shared/aitools/imagesize.py` 的 `probe_image_size()` 只校验 scheme 是 http/https，
**没有**像官方 `utils/ssrf-guard.ts` 那样拦截内网地址与云元数据端点（`169.254.169.254`）。

**当前风险可控**：调用方只传**自己生成的**图片地址（渲染产物），不是用户输入。
**但**：若将来允许用户指定 URL 去探测，就会变成 SSRF 通道。

**处置**：一旦出现"用户可指定 URL"的用法，必须补上 IP 段黑名单（含 IPv6 与重定向后的目标地址），
或改为"先由服务端自己落盘，再探测本地文件"。已记在 `imagesize.py` 的模块 docstring 里。

## R14 · 🟡 共享包日志走标准库，QQ 端靠桥接（易被漏掉）

共享包**不得 import nonebot**（D1 的落地约束），因此日志只能用标准库 `logging`；
而 nonebot 用的是 loguru —— 直接用标准库的话，共享包的 INFO 日志在 QQ 终端与
`qqbot/log/bot-*.log` 里**都看不到**（标准库最后 resort 只打 WARNING 以上到 stderr）。

**处置（M1 已做）**：QQ 端 `plugins/_lib/aitools_host.py` 里加了 loguru 桥接
（`shared.aitools` logger → loguru）。**新增端口/新起子进程时要记得带上桥接**，否则又变成"日志黑洞"。
