**决定**：在 grouphub 仓库内新建共享包，协议解析、包/工具注册表、agent 循环、工具实现**全都只有一份**，backend 与 qqbot 各自 import；部署时两端都要装上它。

**被否掉的方案**

- 只共享协议与循环、工具实现留各端：改动最小，但执行器与参数描述的漂移原地保留，等于没解决主要矛盾。

**落地约束**：共享包不能 import `fastapi` 与 `nonebot`（否则 qqbot 与 backend 依赖交叉）；宿主能力一律走 `ports.py` 抽象。

## D2 · 协议判定：自动探测一次并落库，允许人工覆盖

**决定**：首次遇到某个 `(model, api_base)` 组合时，发一个最小 tool_call 探测请求，判定结果持久化，之后不再重复探测；粒度为 model+api_base（同一模型不同端点能力可能不同）；配置里可人工强制指定走哪种。

**优先级**：人工覆盖 > 已缓存判定 > 自动探测。

**必须守住的细节**
- 探测请求不进气泡、不落 `ai_messages`，只落判定表。
- 探测失败（网络错、额度、超时）**不等于**不支持原生：记 `unknown` 并本次走 text，避免错误结论被永久缓存。
- 运行期若判定失效，允许单次请求内回落 text 并标记待复核，**不得静默改库**。
- 探测有真实成本（计费与延迟），必须按组合去重、带失败退避。

**被否**：纯配置声明（默认值必然与真实模型行为不符，靠人维护）；每次动态判断（同一模型反复踩同一个坑，错误路径复杂化）。

## D3 · 图片策略：两端都渲染 markdown（目标态）· **M0 已验证可执行（2026-10-26）**

**决定**：消息内容统一为 markdown，Web 端引入 markdown 渲染器 + sanitizer，QQ 端用 markdown 消息嵌公网图片 URL，两端一致性最高。

**M0 核实结果**：✅ **D3 可执行**。完整实测记录见 **[`M0-markdown-可行性实测.md`](M0-markdown-可行性实测.md)**，结论要点：

- QQ **群聊**的 markdown 消息（`msg_type=2`）完全可用：粗体/斜体/删除线/行内代码/**代码块**/**表格** 全部正确渲染。
- markdown **嵌图也可用**，但**必须按官方语法带尺寸提示** —— 这是 M0 才发现的硬约束，原设计里没有。
- 纯文本通道（`msg_type=0`）完全不解析 markdown，属预期行为。

**必须守住的实现约束**（M0 实测得出）
1. **图片语法必须是 `![alt #宽px #高px](url)`**，不是标准 `![alt](url)`。
   缺尺寸提示时**手机端只显示 alt 文本**（电脑端有 fallback 能自行取尺寸，所以电脑端看不出来）。
   → 因此**发前必须自动探测图片宽高**：HTTP Range 拉前 64KB，解析 PNG IHDR / JPEG / GIF / WebP 头
   （照腾讯官方 `tencent-connect/openclaw-qqbot` 的 `image-size.ts` 做）。
2. **图片地址要能被加载**：裸 IP、外部公网 https 实测可用；**自建未备案域名实测卡在"加载中"**
   → 长期用已备案域名 / CDN。
3. **一次触发最多被动回 5 条**（错误码 `40034128`）；`msg_type` 单值，markdown 与图片不能同条。
4. 兜底：尺寸探测失败 / 地址加载不出来 → `msg_type=7` 独立图片段，或整段渲染成一张图。

**原"已知前置阻塞"逐条更新**
1. ~~站点无 https~~ → **不阻塞**：裸 IP + http 实测能出图。https 仍是更稳的选择，但不是门票。
2. 平台门槛 → **部分作废**：被动 markdown 消息**本机器人已有权限**（能发、渲染正确）。
   「域名需 ICP 备案」这条**在图片地址上依然成立**（见约束 2），但**不是平台侧拒发**——
   实测平台对未备案域名的图并未报错，只是图片加载不出来。
3. ~~QQ Markdown 可能不支持代码块与 HTML~~ → **代码块被实测证伪**（支持，且是带语法标签/复制按钮的完整卡片）。

**有利事实（仍然成立）**：官方文档明确"markdown 消息内的图片资源请使用可在公网访问的 URL，**开放平台会下载转存该资源**"，因此图片不依赖原链长期存活，直链时效性风险显著降低。

**回退路径**：**暂不启用**。仅在实现遇到阻力时启用（QQ 富媒体发图 / Web 图文混排）。
设计上用 `ImageSink` 抽象保证这个切换**只动 adapter，不动工具层**。

**踩坑留痕**（M0 期间我作废过三个结论，见 `M0-markdown-可行性实测.md` §7）：
① 仅凭手机端截图断言"平台不支持嵌图"；② 把"平台没报错"当成"转存成功"；
③ 过早收口断言"手机上嵌图没戏、砍掉 QQ 端渲染分支"。
→ **渲染类结论必须手机 + 电脑两端都看**；**结论要跟着证据走**。

## D4 · 同步：不复制消息，跨端只作为上下文注入

**决定**：每端各自维护自己的消息时间线；跨端内容只作为 prompt 上下文拼接给模型，保证 AI 知道全局，而用户界面不出现任何代发或镜像消息。

**为什么这是对的选择**：QQ 端无法以用户身份发言，"双向同步"在 QQ 侧必然是伪冒或镜像，观感与归属都会错。不复制消息，就没有回声环、没有幂等键、没有"机器人替我说话"。

**代价（需接受）**：两端时间线视觉上不连续——群里看不到你在网页问的话，网页群会话里也看不到 QQ 原文。缓解手段是把注入的跨端上下文在 UI 上给出可读来源标注（如折叠的"参考：QQ 端最近 3 轮"），仅展示不入库。

**被否**：只回灌 AI 回复 / 用户消息也回灌（均需 source 字段 + 幂等键 + 回声抑制，且存在伪冒观感）；完全不回灌（连上下文都没有，AI 失去全局认知）。
